## 2. 背景与问题定义
当前 benchmark 的核心本质是：
> 给定一份 API 规格（API spec），要求模型按规范实现可运行服务，并通过端到端调用验证。

此前样例集中在 gRPC + KV store，但这只是实例，不应成为数据合成的唯一形态。为避免模型“背模板”，需要扩展到多协议、多领域任务，同时保持能力要求等价。

目标任务应覆盖：
1. 读取并理解 API 文档（接口、请求/响应、状态码/错误语义）
2. 选择或遵循指定技术栈实现服务（HTTP/gRPC/WebSocket/CLI RPC 等）
3. 实现业务逻辑与数据读写/计算流程
4. 处理规范与非规范并存的接口命名（如 `setValue`、`getVal`、`Set_Value`）
5. 启动服务并通过自动化调用验证行为一致性
6. 在指令约束下保证目录结构、命名、端口、依赖版本等遵循度

因此，本 PRD 定义一个“API spec 驱动”的可复用 pipeline，用于批量生成能力对齐、低污染、高多样的实现型任务数据。

---

## 3. 产品目标（Goals）
1. **能力对齐**：生成样本在“读 spec→实现 API→运行验证”的能力维度上与原 benchmark 等价，不明显偏易或偏难。
2. **测试集隔离**：避免 prompt、文件名、端口、参数、叙述模板与已知测试集高度重叠。
3. **任务多样性**：覆盖多协议（非仅 gRPC）、多业务域（非仅 KV）、多命名风格（含非规范命名）与多约束组合。
4. **可验证性**：每条样本可自动评测（编译、运行、RPC 行为、约束符合性）。
5. **可扩展性**：后续可扩展至非 KV 任务（队列、计数器、会话状态等）。

---

## 4. 非目标（Non-Goals）
- 不追求生产级分布式系统语义（如强一致、跨区容灾、分片路由）。
- 不在第一期引入复杂鉴权、TLS、多副本。
- 不构建通用所有语言 runtime，仅优先 Python 主线。

## 6. 能力模型与对齐标准（API Spec 导向）

### 6.1 任务能力拆解
| 能力维度 | 描述 | 典型可观测行为 |
|---|---|---|
| Spec 理解 | 从 API 文档提取契约 | 正确实现 endpoint/method/schema |
| 依赖管理 | 按版本安装包 | 使用 pip/npm/go mod 安装并可导入 |
| 协议工具链 | 使用对应生成/框架工具 | 如 OpenAPI/gRPC/GraphQL 工具链可运行 |
| 服务实现 | 业务逻辑与接口映射 | 读写/计算/校验逻辑正确 |
| 非规范命名兼容 | 处理命名不一致接口 | 同时实现 `setValue` 与 `getVal` 等异构风格 |
| 进程控制 | 启动并保持服务 | 绑定指定端口并可被客户端访问 |
| 指令遵循 | 严格执行路径/命名/端口 | 文件位置与类名符合要求 |
| 元认知设计 | 分析 benchmark 并设计 pipeline | 给出能力对齐与防污染策略 |

### 6.2 对齐原则
- **等价而非同构**：保持能力维度一致，但避免同文本模板。
- **多轴随机化**：在命名、端口、字段、操作语义上做受控变化。
- **约束保持**：关键链路（读 spec→实现→运行→验收）必须完整。
- **命名鲁棒性**：同一批数据中必须包含“规范 + 非规范”接口命名模式。

## 7. 需求清单

### 7.1 功能需求（Must）
1. 模板生成器可参数化输出任务说明（自然语言）。
2. 任务至少包含两类 API 操作（如读/写、创建/查询、提交/回滚）。
3. 自动生成 API spec（OpenAPI/proto/GraphQL SDL/自定义接口文档）并校验可解析。
4. 自动生成参考解（server + 可选 client）。
5. 自动评测脚本验证端到端行为。
6. 自动污染检测（n-gram、结构签名、路径签名）。
7. 输出难度标签与能力标签。
8. 每批次至少 30% 样本包含非规范接口命名（如 `setValue`,`getVal`,`fetch_data` 混搭）。

### 7.2 功能需求（Should）
1. 支持多语言说明（中文/英文/混合）。
2. 支持注入“附加分析任务”（如让模型解释 benchmark 难点）。
3. 支持故障注入样本（版本冲突、字段错位、端口占用）。

### 7.3 非功能需求
- **可复现**：同 seed 生成结果一致。
- **吞吐**：单机每小时生成并验证 >= 300 样本（L1-L3 混合）。
- **质量**：自动评测通过率（参考解）>= 99%。
- **可追溯**：每条样本具备 lineage（模板ID、seed、规则版本）。

## 8. 数据合成 Pipeline 设计

### 8.1 总体流程
1. **Capability Spec 定义**：声明目标能力向量与难度区间。
2. **Spec Generator 实例化**：生成 API spec（协议可插拔）+ 任务说明。
3. **Reference Solution 生成**：生成 server / client / run 脚本（按协议）。
4. **Execution Validation**：安装依赖、启动服务、API 回归、约束检查。
5. **Contamination Filter**：与保留集做文本/结构相似度筛查。
6. **Diversity Balancing**：按维度重采样，防止分布塌缩。
7. **Packaging & Split**：导出 train/dev/test(hidden)。

### 8.2 任务 DSL（示例字段）
- `protocol`: `grpc` / `http-openapi` / `graphql` / `custom-rpc`
- `domain`: `kv` / `inventory` / `scoreboard` / `ticketing` / `rate-limiter`
- `service_name`: 如 `ValueHub`, `OrderPulse`
- `operation_set`: 如 `createItem`, `getVal`, `setValue`, `list_items`
- `naming_style_mix`: `camelCase` + `snake_case` + `abbrev`
- `state_model`: `dict` / `in-memory-index` / `append-log`
- `data_schema_complexity`: 标量 / 嵌套对象 / 列表分页
- `error_contract`: `code+message` / `status_only`
- `port`: 随机高位端口
- `path_constraints`: 输出路径规则
- `extra_requirement`: “先分析难点再实现” 等

### 8.3 变异策略
- **协议层**：gRPC/OpenAPI/GraphQL/custom RPC 切换。
- **领域层**：KV、库存、排行榜、工单、限流计数等。
- **命名层**：规范+非规范 API 混合（`setValue`,`getVal`,`upd_item_v2`）。
- **结构层**：操作数量（2~6）、参数复杂度、错误返回结构。
- **流程层**：是否要求后台运行、是否要求健康检查/重试。
- **约束层**：指定版本、固定目录、类名、日志输出格式。

## 9. 防污染与去重策略

### 9.1 污染来源
- 与公开 benchmark 文本高度重叠
- 与已有训练语料中的“固定指令模板”重复
- 引用固定路径/端口/类名造成可记忆 shortcut

### 9.2 控制措施
1. **模板指纹黑名单**：禁止复用高风险 prompt 片段。
2. **语义近邻过滤**：embedding 相似度超过阈值则丢弃。
3. **结构签名扰动**：随机化文件名、端口、RPC 命名。
4. **留出集隔离**：hidden test 的模板族与训练模板族不重叠。
5. **人工抽检**：每批次抽样 5% 做语义/结构双检。
6. **协议/领域隔离**：hidden test 至少包含 1 个 train 中未出现的“协议×领域”组合。

### 9.3 指标
- 近似重复率（MinHash）< 1%
- 与保留 benchmark 的语义相似度 P95 < 阈值 T
- 模板族重叠率（train vs hidden）= 0

## 10. 难度分层设计
- **L1（基础）**：2 个 API 操作、单存储结构、基础读写。
- **L2（标准）**：版本锁定 + spec 遵循 + 后台运行。
- **L3（进阶）**：非规范命名 + 错误契约 + 并发访问校验。
- **L4（挑战）**：跨协议/混合语言指令 + 隐式约束 + 多步骤验收。

难度标签通过如下信号综合打分：
- 指令长度与约束数量
- 工具链步骤数
- 失败模式数量（端口/版本/路径）
- 需要的跨文件推理深度

---

## 11. 评测与验收

### 11.1 自动评测项
1. 依赖版本检查（pip freeze 匹配）
2. API spec 语法与可解析性检查
3. 服务器启动检查（端口监听）
4. API 功能测试（写后读、一致性、默认值/错误码）
5. 指令遵循检查（路径、命名、类名）
6. 稳定性检查（N 次请求成功率）
7. 命名兼容检查（非规范接口名称必须可访问且语义正确）

### 11.2 业务验收标准（MVP）
- 生成 500 条样本，参考解自动评测通过率 >= 99%
- L1-L4 样本占比可配置，且任一层不少于 10%
- 污染指标满足第 9.3 条约束
- 每条样本输出完整元数据与可复现实验 seed

---

## 12. 里程碑
1. **M1（1周）**：Capability Spec + 多协议 DSL 初版 + 20 条样本手工验证
2. **M2（2周）**：自动生成与自动评测打通，支持 200 条批处理
3. **M3（3周）**：非规范命名注入器 + 污染检测 + 多样性平衡上线
4. **M4（4周）**：发布 MVP（500+ 样本）并完成质量报告

---

## 13. 风险与缓解
- **风险**：难度漂移（过易/过难）  
  **缓解**：引入基线模型回放，按通过率闭环调参。

- **风险**：多样性不足（模板化严重）  
  **缓解**：增加 DSL 维度并做分布约束采样。

- **风险**：污染误检/漏检  
  **缓解**：多策略融合（n-gram + embedding + 结构签名）并人工复核。

- **风险**：环境不稳定导致评测噪声  
  **缓解**：容器化评测、固定镜像、重试机制。

## 15. 附录：首批样本生成建议
- 每批 100 条，按 L1:L2:L3:L4 = 3:4:2:1
- 协议比例：gRPC 35%、HTTP(OpenAPI) 35%、GraphQL 20%、custom RPC 10%
- 领域比例：KV 25%、inventory 20%、scoreboard 20%、ticketing 20%、rate-limiter 15%
- 非规范命名样本占比：总体 >= 30%，其中 L3/L4 >= 60%
- 语言比例：中文 40%、英文 40%、混合 20%
- 端口范围：`[20000, 60000]`，避免固定端口记忆
- API 命名库与字段命名库分离，降低共现模式记忆
